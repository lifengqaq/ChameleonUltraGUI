# ISO 14443-4 / CPU card support

The firmware implements ISO-DEP over ISO 14443-A at 106 kbit/s. ISO-DEP is a transport, while generic ISO 7816 files, EMV/PBOC and NDEF are application families. Selecting an application family in the GUI does not add ISO 14443-B support or make every CPU card compatible.

## Native card and slot management

Create or edit a CPU card through the normal card library dialog. This dialog contains basic identity information (UID, ATQA, SAK and ATS) and the application family. Use the card's **Edit data** action for files, a versioned JSON profile and emulated authentication settings. The corresponding slot action reads and edits the device's existing CPU image. Editing data preserves the card ID, name, folder, color and radio identity.

The Tools page retains the advanced APDU console. The separate CPU emulation page has been removed. Upload, readback and persistence use the normal slot management flow.

CPU data may be an identity-only entry, a CFS1 filesystem image, or a legacy table of alternating APDU prefix and response arrays. Card JSON export/import preserves these representations and the bounded-dump archive metadata. An archive that cannot fit the device is explicitly marked archive-only and cannot silently upload as an identity-only card.

## Reader sessions and APDU console

1. Enter reader mode and open a session with command **6007**, payload `01`.
2. Send successive APDUs with **6004**, preserving RF power, block numbers and the selected application.
3. Close the session with **6007**, payload `00`, when finished.

Opening returns `uid_len | uid | atqa[2] | sak | ats_len | ats` (ATS includes TL; no CRC). Closing returns device success (`0x68`). APDU operations return HF success (`0x00`) plus the complete response including SW1/SW2. Transport failures return an error with no response payload; incomplete chained data is not a successful APDU. A legacy first call to 6004 can still open a session automatically. Other reader operations, mode changes and transport errors invalidate it.

The RC522 path advertises FSD=48, limits each transmit frame to its 64-byte FIFO, derives FSC/FWT from ATS, fragments commands and reassembles responses. Limits: command 4–260 bytes, response 512 bytes, 128 exchanges, two command retransmissions, eight WTX requests, at most five seconds for an individual WTX wait. NAD and faster data rates are not supported. CRC_A is checked on every received frame.

The GUI provides SELECT MF, READ/UPDATE BINARY and READ/UPDATE RECORD templates. Templates populate the editor; **Send** executes. Multiple lines stop on the first status other than `9000`. Optional ISO 7816 handling follows `61xx` with GET RESPONSE and retries `6Cxx` only for unambiguous case-2 reads. Writes and authentication are not automatically repeated at the APDU application layer. Procedure handling is bounded to 16 exchanges and 4096 response data bytes.

## Saving readable data and authentication

**UID / RF identity only** saves without authentication. **Save readable data** reads a supplied plan of known AID/FID paths, or the record ranges advertised by captured EMV AFL data. A generic CPU card cannot be universally enumerated by this feature. NDEF provides a starting AID/file plan that may need card-specific adjustment.

A protected operation returning `6982` opens an authentication dialog. Credentials are prefilled only: PIN `000000`, DES `FFFFFFFFFFFFFFFF` (eight bytes), and a separate 3DES option accepting 16 or 24 bytes. No default is submitted automatically and credentials are never rotated automatically. The configured PIN reference, encoding, key reference and algorithm must match the particular application. Supported external authentication is an explicit eight-byte DES/3DES challenge-response profile, not DESFire mutual authentication, secure messaging or an EMV payment cryptogram implementation.

Remaining tries are taken only from an actual failed authentication response `63Cx`. Other failures leave the count unknown; `6983` and `63C0` block further submission. A last observed count of one is red and requires a separate confirmation before submitting. No empty VERIFY or generic GET DATA query is sent to obtain a counter. A transport timeout disables resubmission in that dialog because delivery may already have occurred. Counts remembered in memory are observations from prior responses, not a live counter query.

Archives record the attempted plan, readable files, failures, completeness for that plan, and captured public responses. They explicitly state `universalComplete:false` and `keysExported:false`. They do not reconstruct original keys, dynamic transaction behavior or guarantee compatibility with the original reader. Data read after authentication is not made publicly readable in an emulation image: access conditions and emulated credentials must be configured explicitly in **Edit data**.

## Filesystem emulation and firmware compatibility

A CFS1 image supports up to 16 nodes and 3252 bytes total. The MCU handles SELECT, READ/UPDATE BINARY, READ/UPDATE RECORD and GET RESPONSE without a phone. Version 2 adds a 44-byte SEC1 authentication trailer within the same capacity. It supports a 4–12 digit PIN, an eight-byte DES or 16-byte two-key 3DES key, separate retry limits from 1 to 15, locking, VERIFY, GET CHALLENGE and EXTERNAL AUTHENTICATE. The reader dialog additionally accepts 24-byte 3DES keys; the device's emulated security configuration does not.

Command **6009**, subcommand `07`, returns `[02,03]` for image version 2 and the PIN/key feature bits. This is a device-firmware query, not a card authentication attempt. The GUI checks this capability before changing a target slot for a secured image, rejecting incompatible firmware before staging data. The query works regardless of the slot's current card type. Images are validated before staging, committed atomically, and read back for comparison.

Authentication state and outstanding challenges reset on RF reset or slot reload. Challenges require the device RNG. Failed-attempt counts live in the mutable image and are persisted through the existing slot save/load flow; abrupt power loss before a save can restore the last saved count. This is not immediate power-loss-safe counter storage.

The emulator handles command/response chaining, expected block numbers, R(ACK)/R(NAK), duplicate blocks, negotiated FSD/CID, 106 kbit/s PPS, DESELECT and bounded WTX. Incoming NFCT bit lengths and CRC_A are normalized before ISO-DEP parsing.

## Legacy response tables

Legacy tables match 1–16-byte prefixes, longest match first. Twelve responses of 2–253 bytes fit the persistent per-slot layout after saving. Four additional responses of 254–260 bytes are volatile and must be reuploaded after power-off or slot reload. Responses include SW1/SW2; invalid sizes fail instead of truncating. Duplicate prefixes replace an entry; unknown commands in a populated table return `6D00`.

Command **6003** uploads `cmd_len[1] | prefix | resp_len[2 BE] | response`; a single zero clears the table. **6008** returns the count for an empty request or one entry for its zero-based index. **6002** sets the anti-collision identity. With an empty table, 6000/6001 provide the existing bounded host responder path. Static tables alone do not implement mutable files or authentication.

## EMV discovery and verification

Command **6005** selects PPSE, the first advertised AID, parses its PDOL and reads validated AFL records in one uninterrupted session. Non-TTQ PDOL values are zero during discovery; there are no guessed PDOL-length retries. Partial responses and status words are retained. This is not a complete EMV payment kernel.

Firmware regression tests exercise the production protocol and filesystem engines, authentication vectors, counters, locking, resets and replay handling. GUI regressions cover serialization, bounds, explicit credential submission, counter display, last-attempt confirmation, UID-only saving, native data editing and PageStorage restoration. Builds and full GUI tests run in GitHub Actions because the local device has no Flutter SDK or C compiler.

RF timing, reader interoperability, actual application authentication, standalone use and power-cycle persistence still require the matching firmware on a ChameleonUltra and suitable physical cards. Build and unit-test results do not replace those measurements.
