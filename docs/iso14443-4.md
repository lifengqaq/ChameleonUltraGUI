# ISO 14443-4 / CPU card support

The firmware implements ISO-DEP over ISO 14443-A at 106 kbit/s. The matching GUI branch adds **Tools → CPU / ISO 14443-4**. Reader transport and application behavior are separate: an APDU console can access files exposed by a selected application, subject to that application's normal authentication and access conditions.

## Reader

1. Enter reader mode and open a session with command **6007**, payload `01`.
2. Send successive APDUs with **6004**, preserving RF power, block numbers and the selected application.
3. Close the session with **6007**, payload `00`, when finished.

Opening returns the existing scan format: `uid_len | uid | atqa[2] | sak | ats_len | ats` (ATS includes TL; no CRC). Closing returns device success (`0x68`). APDU operations return HF success (`0x00`) plus the complete response including SW1/SW2. Transport failures return an error and no response payload; incomplete chained data is never reported as a successful APDU. A legacy first call to 6004 can still open a session automatically. Other reader operations, mode changes and transport errors invalidate it.

The RC522 path advertises FSD=48, limits each transmit frame to its 64-byte FIFO, derives FSC/FWT from ATS, fragments commands and reassembles responses. Limits: command 4–260 bytes, response 512 bytes, 128 exchanges, two command retransmissions, eight WTX requests, at most five seconds for an individual WTX wait. NAD and faster data rates are not supported. CRC_A is checked on every received frame.

The GUI provides editable SELECT MF, READ/UPDATE BINARY and READ/UPDATE RECORD templates. Templates populate the editor; **Send** executes. Multiple lines run in the same session and stop on the first status word other than `9000`. Optional ISO 7816 handling follows `61xx` with GET RESPONSE and retries `6Cxx` only for unambiguous case-2 read commands. Writes are not repeated at the APDU application layer. Procedure handling is bounded to 16 exchanges and 4096 response data bytes.

## Emulation

The emulator handles command and response chaining (PCB bit `0x10`), expected block numbers, R(ACK)/R(NAK), duplicate blocks, negotiated FSD/CID, 106 kbit/s PPS, DESELECT and host WTX. Incoming NFCT lengths are converted from bits and CRC_A is removed before ISO-DEP parsing.

- Command matching uses **1–16-byte prefixes**, with the longest match winning.
- **12 responses of 2–253 bytes** use the existing per-slot persistent layout. Save slot data to commit them to flash.
- **4 additional responses of 254–260 bytes** are volatile. They must be uploaded again after power-off or slot reload. Export includes them while they are loaded.
- Responses include SW1/SW2. Capacity violations and malformed lengths return an error, rather than silently truncating or accepting data.
- Duplicate command prefixes replace existing entries. Unknown commands in a populated offline table return `6D00`.
- With an empty table, 6000 polls for a pending APDU and 6001 supplies a BE16-length response. WTX is bounded; an expired host response returns `6400`.
- Static responses do not implement a mutable application filesystem, application keys, secure messaging or dynamic cryptographic calculations. These require a specific application implementation or host responder.

Command **6003** uploads `cmd_len[1] | prefix | resp_len[2 BE] | response`; a single zero byte clears the table. New command **6008** returns a one-byte count for an empty request, or the same prefix/BE16-response encoding for a one-byte zero-based index. Command **6002** sets the anti-collision identity. The slot's persistent struct is unchanged.

## EMV discovery

Command 6005 still returns the original packed format, with little-endian response lengths. It selects PPSE, the first advertised AID, parses its PDOL and reads validated AFL records in one uninterrupted session. BER-TLV parsing handles constructed templates and long-form lengths; record loops use 16-bit counters. There are no guessed PDOL-length retries. Non-TTQ PDOL values are zero during this discovery scan. Card status words and any completed pairs are preserved when discovery stops; the result is not a complete EMV payment kernel.

## GUI data and verification

The CPU tool supports captured exchanges, an editable versioned JSON profile, saved card-library entries, selected-slot upload and selected-slot readback. A saved ISO-DEP `CardSave.data` contains alternating prefix and response arrays. Generic card JSON export/import therefore retains both identity and APDU rules; older identity-only cards remain readable. Capture takes the first 16 command bytes explicitly; inspect and edit duplicate or ambiguous prefixes before uploading.

`tests/iso14443_4_test.c` exercises the production protocol engine with CRC fixtures, persistent sessions, bidirectional chaining, duplicates, R(NAK), CID, WTX, PPS, DESELECT, errors and overflow under AddressSanitizer/UBSan in GitHub Actions. The GUI includes parser, profile round-trip, wire length, status, capacity, session and ISO 7816 procedure regressions. Full firmware and application builds also run in Actions; no compiler or Flutter SDK is installed locally for this work.

RF timing, reader interoperability, card-specific authentication and physical writes still need a ChameleonUltra and matching test cards for hardware verification. Build success and protocol fixtures are separate from those measurements.
